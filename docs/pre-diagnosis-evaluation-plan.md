# ticket-doctor：预诊断评测实施方案

> 编写日期：2026-10-01。用于 GLM5.3Flash 接续评测建设。本文是待实现技术方案，不表示相关功能、候选 case 或真实模型评测已经完成。
> 本轮仅新增本文；不修改业务代码、不实现自动修复、不创建分支、提交或 PR。
> 项目现有运行状态与历史基线继续以 `docs/status.json` 为事实源；本文中的新增协议、模块、命令均为设计。

## 1. 决策与可验证目标

### 1.1 本次确定的方向

维持原始业务：测试提交 Bug → 自动触发调查 → 只读查询相关日志与故障版本代码 → 输出带证据、边界和待补材料的预诊断 → 回写。

预诊断可以停在有依据的局部定位、候选原因或有效补证；不要求每个工单锁定最终根因。本文不包含 Agent 编辑代码、执行修复、验证新补丁、提交代码或创建 PR。案例制作人员复现历史故障、核验历史已修复版本，是制作评测材料的工作，不是新增自动修复业务。

**case 选择结论：优先公开历史 Bug，先验证 FastAPI 7，再考虑 12、5；通过准入后才正式纳入。** 不以自己写两个故障服务作为开工前置条件。现有 checkout-timeout 五条合成 case 保留作 harness 自测，单列结果，不用于声称真实诊断质量。

**六工程件结论：六项所代表的能力大体需要，但第一项应改为“可信案例材料与标准”，其余应尽量复用现有实现。** 不建设六套独立系统，不先做规则自动进化、复杂裁判平台或完整微服务实验场。

### 1.2 验收目标

| 编号 | 可验证目标 | 验证依据 |
|---|---|---|
| G1 | 每个正式 case 的现象、材料、故障版本和判定依据可追溯 | 准入记录、来源、材料 hash、完整 SHA、人工复核 |
| G2 | 能区分已知真实根因与本轮证据支持的判断 | 每轮允许结论、必需事实、禁止断言及补证目标 |
| G3 | 同一调查能完成缺材料、补证、反证的多轮过程 | 生产编排、多轮 trace、同调查不同 run、历史引用 |
| G4 | 分数不会把未展示内容、错误版本或无关引用算作有效支持 | 可见性记录、代码内容核验、评分正反例 |
| G5 | 私有答案及未来材料不会进入诊断 Agent 的能力范围 | 隔离预检、实际工具访问测试、逐轮材料 hash |
| G6 | 能分别检查模型原输出、程序校验后结果、实际回写 | 三阶段输出记录、正式渲染与捕获发送端 |
| G7 | 两次评测的差异可解释、评分可离线重放 | manifest、冻结评分、全部试验结果、失败归因 |

以上是评测工程验收目标。初始真实模型诊断分数即使较低，也不影响评测工程验收；不得为了达到一个任意正确率门槛改宽评分标准。

### 1.3 已确认事项与低风险假设

- 用户已明确六工程件清单，业务仍限于预诊断；本轮没有其他实质性问题需要确认。
- 文档采用仓库现有 Markdown 风格；新增评测仍在同一仓库，不建立新业务服务。
- 默认离线评测，不发送真实 IM 消息。回写通过现有正式投递链路和捕获发送端验证。
- 首期最多三轮，先跑小规模样本，真实模型探索基线每套配置完整跑三次。这是成本可控的初始设计，均允许显式配置。
- 第一阶段人工复核语义评分，不假定已有可靠模型裁判。
- 不假定本机具备 Docker、历史 Python 依赖、可用模型凭据或已批准调用预算；实施时分别预检，缺少时保留不依赖它们的工作成果。
- GLM5.3Flash 是推进实现的模型选择，不自动等于被评测的诊断模型。实际 provider、API model ID 和预算由实施环境确认，本文不猜测接口标识。

## 2. 现有能力、缺口与复用边界

本节以本轮只读检查的 HEAD `bb5bb4bb1dae0d9346e598ad48129ed300d1cfd5` 为依据；实施前必须重新核对差异。

| 现有位置 | 能复用什么 | 本期需要补什么 |
|---|---|---|
| `src/evals/runner.ts` | 单轮准备、真实 Store sink/resolver、独立 case 状态 | 多轮、trace、超时/异常收口、三阶段输出、正式回写 |
| `src/evals/types.ts` | 旧 benchmark 与评分字段 | 新协议、逐轮标准、nullable 指标、family/split、准入状态 |
| `src/evals/benchmark.ts` | 读取 benchmark、旧 locator | 完整 SHA、内容验证、材料目录 hash、严格 schema |
| `src/evals/scorer.ts` | UID/E# 解析、部分概念检查与引用统计 | 允许追问、语义复核、可见性、重要断言检查、适用分母 |
| `src/diagnosis/orchestrator.ts` | 正式执行、预算/取消、RunSession、finalize | 评测复用此路径；不重新实现业务状态机 |
| `src/diagnosis/run-session.ts` | 历史条目、工具执行、usage | 导出及必要的只读观察接口 |
| `src/diagnosis/finalize.ts` | reply/report 正式保存、渲染、投递记录 | 捕获 raw 结果及校验 issues；不要用评分逻辑替代它 |
| `src/agent/pi-engine.ts` | 六个受限工具、request_info、submit_report、会话事件 | 验证能否观察实际模型请求；无法观察时明确观测等级 |
| `src/evidence/render.ts` | 线上共享渲染与截断规则 | 重放验证及关键内容展示范围记录 |
| `src/sources/code.ts`、`src/sources/logs.ts` | 固定 Git tree、文件日志源 | 权限预检、材料范围验证；失败时才做必要最小修正 |
| `tests/integration/pipeline.test.ts` | 多轮续接、正式回写与假发送端示例 | 从固定断言提升为可重用的多轮 case harness |

已核实的重要限制：

1. 当前 eval 不传 SessionSink，任何 `reply` 都判错，包括合理追问；没有正式 finalize 与投递验证。
2. `search_code` 可以持久化最多五十处命中，而共享 renderer 默认只预览前八处；现评分按全部入库证据计算召回。
3. `read_code` 的 excerpt 可被截断，codeRef 仍保留原始行范围；区间包含 gold 行不代表关键内容已展示。
4. 代码 gold locator 没有 SHA；现匹配只检查仓库、路径和行区间。
5. requiredConcepts 使用关键词包含，不能可靠识别否定；forbidden 检查也不能保证处理所有重复出现。已有测试通过不等于语义评分可信。
6. 当前重点检查最高置信度假设，不能覆盖摘要、已确认事实、其他假设中的重要错误断言。
7. benchmark hash 只覆盖 benchmark JSON，没有覆盖日志、源码、规则、模型配置与运行预算。
8. `modelTurns` 当前随工具执行事件递增，不能直接当作模型 API 请求次数使用。
9. 正式主流程按发生时间选提交，不等于有真实部署 SHA 证明；环境字段也不等于完整材料隔离。

**实现原则：评测暴露这些问题，不偷偷修正被评测对象。** 若评分升级导致结果变化，换 scorer 标识并重跑基线。若最小生产观测接口必不可少，可增加可选观察器；不得顺便重构提示词、诊断策略、源码检索或生产适配。

## 3. case 如何选取

### 3.1 主评测的选择顺序

主评测优先满足：业务现象明确、有可信日志或请求响应材料、有完整故障源码 SHA、能通过当前工具读取、能人工建立当轮判断标准。

| 候选 | 选择理由 | 正式接纳前的工作 | 适用范围 |
|---|---|---|---|
| FastAPI 7 | 非法受约束 decimal 输入出现 500，适合异常日志与源码调查 | 历史依赖复现、验证触发器、采集与故障 SHA 对应的日志 | 首个端到端主线候选 |
| FastAPI 12 | 可选 HTTPBearer 的错误 scheme 行为有明确预期 | 固定请求、配置、响应与版本；必要时加最小示例服务 | 认证组件行为诊断；只读分析 |
| FastAPI 5 | 嵌套 response model 字段过滤行为可检查 | 固定请求响应、业务预期、故障源码 | 正常状态码下的行为缺陷 |
| RootCauseBench | 可补充误导部署、延迟出现、证据不足等能力 | 确认所需材料当前工具可取得，建立自己的轮次标准 | 单列补充诊断集 |
| RCAEval RE3 | 可补充跨服务异常和日志定位 | 核对单例遥测、根因服务；源码 SHA 未确认时不评分代码版本 | 单列日志定位补充集 |

BugsInPy 提供历史故障/已修复版本与触发测试，但仍需要转换成预诊断调查材料。不能直接把它的修复测试通过率当作 ticket-doctor 诊断正确率。[BugsInPy 官方说明](https://github.com/soarsmu/BugsInPy)

RootCauseBench 提供冻结事故材料，其核心通过条件是罪魁提交匹配；这与本项目的证据支持、补证和回写目标不同。它不能替代完整故障 Git 源码的版本验证，也不能直接沿用其分数。[官方仓库](https://github.com/edgedelta/root-cause-bench)、[数据与评分说明](https://github.com/edgedelta/root-cause-bench/blob/main/datasets/rootcausebench/README.md)

RCAEval RE3 可用于异常服务和栈位置定位。故障源码与部署 SHA 未核对时，对代码版本指标记不适用；日志中的行号不自动证明某 Git 版本。[官方数据与使用资料](https://github.com/phamquiluan/RCAEval)

不先接入 SWE-bench 修复任务、LogHub 随机日志或完整微服务故障平台：它们不能以当前最低成本直接回答本期预诊断问题。以后可以重新评估，本文不安排实现。

### 3.3 正式准入门槛

候选状态：`candidate → qualified → admitted`。无法证明成立的案例标为 `deferred`，不得用造一份错误日志来补齐。

正式主线 case 必须全部满足：

1. **现象可描述**：有输入、实际结果、合理预期、发生时间/时间未知状态、服务/服务未知状态。
2. **来源可查**：原资料、采集环境、转换步骤、来源许可与保存/再分发边界记录完整；许可不明时只保留链接，暂缓打包。
3. **版本可核验**：故障源码完整 SHA 可解析；日志、配置、请求响应与该版本的对应关系有记录。
4. **材料真实或明确重建**：来自原事件、原复现或已记录环境的历史故障复现。人工派生时间、请求 ID、包装日志明确标记。
5. **当轮标准可判**：至少有可判事实，或明确需要补证/保持未知；不能只给一个最终答案字符串。
6. **能力相匹配**：当前日志/代码工具能提供必要信号；必须依赖未实现指标/trace 工具的 case 暂缓，不把所有遥测硬塞成日志。
7. **预算可接受**：材料规模与调查轮数受控；准备失败可诊断，能在预设预算内完成材料回放。
8. **答案可隔离**：修复补丁、未来材料、gold、解释答案的文件名/文本可排除。
9. **标准经过复核**：复核者确认事实、因果和允许结论，不仅确认补丁改过某行。

仅有可信原事故快照但无法重新启动环境的 case，可以接纳到 `verified_snapshot` 补充层；必须注明因果依据与复现限制。不要将它混报成已复现历史故障主线层。

### 3.4 材料制作与复现

每个候选先制作一份资格报告：来源、故障 SHA、环境锁定、触发输入、预期行为、实际结果、原始日志、退出码、困难及接纳判断。

- 优先复用 BugsInPy 原触发器；需要 HTTP 流量时用最小服务包装原故障库，不能重写故障逻辑。
- 同一触发输入在历史故障版本和历史已修复版本分别运行。对照核验的是预期业务行为，不是统一断言“500/200”；校验失败的正确结果可能是 422，认证错误也有自己的约定。
- 两次环境除目标代码差异外尽量一致；必须改变依赖或配置时，记录它并人工判断能否归因。
- 原始日志原样保存。兼容 `FileLogSource` 的 TSV 另存，格式为时间、级别、正文；多行栈需要保留原行映射，不丢异常关键上下文。
- 实际复现时间、归一化评测时间、历史提交时间分别保存。改写时间仅用于回放，标为 `derived_metadata`，不能冒充原事故时间。
- 服务包装、请求响应采集、启动时版本记录标为 `reconstructed_harness`；其版本与被诊断库版本分别记录。
- 历史修复源码、补丁、回归测试只在制作侧。它们能辅助验证，不单独构成根因 gold；还要解释故障路径为何产生已观察现象。
- 首次资格验证后可冻结快照做日常诊断回归；依赖、包装、触发器或材料生成逻辑变化后重新资格验证。

快照回归证明同一材料条件下的诊断表现，不能替代服务真实运行验证，也不能证明真实远程日志平台接入有效。

### 3.5 覆盖矩阵与首批规模

首个历史故障通过后，用它验证数据协议和运行器；随后优先扩到三个独立故障族。首批目标六至十条调查轨迹，数量是建设目标，不是已接纳数量。

| 轨迹类型 | 本期覆盖 | 关键预期 |
|---|---|---|
| 材料充分 | 是 | 给出达到证据深度的预诊断，引用相关内容 |
| 首轮缺材料、随后补证 | 是 | 第一轮补问关键字段，下一轮利用新增材料 |
| 补充仍不足 | 是 | 不把预算耗尽或空查询当作排除故障 |
| 新反证 | 是 | 降低、更新或撤回被推翻的判断，说明依据 |
| 相似干扰 | 是 | 不因关键词、时间相近就断言因果 |
| 版本或环境无法确认 | 是 | 说明边界，代码归因不能冒充已验证 |
| 回写/运行异常 | 工程自测 | 记录失败、按既有规则重试，其他 case 能继续 |

不能为了凑齐反证而伪造同一故障运行的互相矛盾日志。可采用不同请求/实例的真实复现、可信无关材料，或明确标记的人工脚本自测；重新判断当轮允许结论。缺乏可信反证来源时，该主线能力标覆盖缺口，工程用例不能替代它。

同一 Bug 的完整材料、缺材料、噪声、不同轮次视图共享 `familyId`，不能当成多个独立根因。同一 family 不跨 development/holdout。三个 FastAPI 故障可支持初期不同机制验证，但不能证明跨语言或跨框架泛化。

## 4. 对六工程件的评价与修正

| 工程件 | 本期判断 | 修正后的最小实现 |
|---|---|---|
| 1. 可运行受控诊断对象 | 可信案例依据必需；自己造服务可选 | 历史 Bug 资格验证与材料冻结。现有合成 fixture 做工程自测 |
| 2. 多轮运行器 | 必需 | 复用 executeRun/RunSession/Store/finalize/投递，新增逐轮驱动与导出 |
| 3. 判分器与反例 | 必需，优先完成 | 确定性硬检查 + 人工语义复核 + 正反例校准 |
| 4. 可见性三层 | 必需，需补报告使用层 | 本次源返回、入库、实际工具返回/请求上下文、报告引用分别记录 |
| 5. 隔离与防作弊 | 必需 | 能力范围闭包、逐轮挂载/配置、Git tree 检查、访问反例 |
| 6. manifest/归因/冻结基线 | 必需 | 全材料与配置指纹、离线重放、全部试验、分层失败 |

原建议的几个过强表述应删除：

- “只有自己造 Bug 才有可信答案”：不成立；历史故障复现和可靠事故证据同样可建立依据。
- “坏版 500，好版 200 就证明根因”：不充分；必须核对业务预期、同一条件和实际故障路径。
- “反例都必须先失败”：不需要。先运行记录；已正确处理的反例保持通过，有误判才要求修复前后对照。
- “纯函数重放相同就证明模型看见”：只能验证 renderer。上下文压缩、消息删减或请求构建仍可能改变可见内容。
- “把答案移到 standards 目录即可”：目录名不构成权限边界，还要检查源码 tree、路径、prompt、会话、日志与未来输入。
- “真实模型同输入必得同输出”：无法承诺。可承诺输入核验、trace 复盘、确定性评分重放；多次运行的波动应如实保存。

## 5. 评测除了 case 还需要什么

| 配套 | 不具备时的后果 | 本期交付 |
|---|---|---|
| 每轮判定标准 | 把猜中隐藏根因当成功，把合理补问当失败 | 私有逐轮 gold 与可接受行为 |
| 覆盖/分组/数据划分 | 多个变体冒充多个独立样本，调参泄漏 | family、sourceTier、development/holdout |
| 一致执行环境 | 测到的是评测替身或错误版本 | 共用生产链路、材料预检、预算限制 |
| 可追踪观测 | 无法辨别取材、输出与校验问题 | trace、三阶段输出、可见性等级 |
| 有效评分与人工复核 | 关键词刷分，正确引用救活错误结论 | 硬检查、人工 rubric、校准记录 |
| 工程边界 | 抄答案、读未来材料、跨 case 污染 | 权限/隔离测试、每次试验新状态 |
| 可比较记录 | 分数变化原因不明 | manifest、逐 case 结果、冻结基线 |
| 成本和失败口径 | 删除失败运行使成功率虚高 | 总数/有效数/缺测数、耗时、usage、工具数 |
| 人工使用价值 | 分数好但开发仍要重做取证 | 初步可用性复核；后续真实效率对照实验 |

## 6. 数据协议与目录设计

### 6.1 材料分离

建议新增的工作目录统一放在 `data/eval-v2/`，不改变现有 fixture 格式：

```text
data/eval-v2/
  catalog/                   # 制作侧来源、准入、family/split；不送入模型
  private/<case-id>/          # truth.private.json、未来轮输入、历史修复、资格报告
  public/<case-id>/round-1/   # 本轮可用 logs、repo、配置/请求响应资料
  public/<case-id>/round-2/   # 下一轮材料；第一轮不能配置或挂载此目录
  runs/<suite-run-id>/
    manifest.json
    <case-id>/<trial-id>/trace.jsonl
    <case-id>/<trial-id>/outputs.json
    <case-id>/<trial-id>/score.json
    <case-id>/<trial-id>/review.json
    summary.json
    summary.md
```

这些目录名用于组织，隔离由第 10 节的工具能力与材料范围实现。private 不注册为 repo，不配置为 logDir，不进会话资源加载。大体积源码/日志先用本地工件与 hash，不自动提交到主仓库；公开小样本需确认许可和答案隔离后再考虑版本管理。

控制器读取公开描述及私有标准；诊断引擎只收到当前用户消息、已发布的材料范围和正常历史上下文。case ID、BugsInPy 编号、原 Issue 链接、答案提示性测试名不注入模型输入。

### 6.2 公开 case 描述

下面是控制器消费的数据示例，不是当前已支持的配置。SHA 和消息内容在资格验证后填入，禁止将占位值运行成正式 case。

```json
{
  "schemaVersion": "prediagnosis-case-v2",
  "caseId": "fp07-clarify",
  "familyId": "fastapi-7",
  "split": "development",
  "sourceTier": "reproduced_history",
  "publicBenchmark": true,
  "admission": "candidate",
  "maxRounds": 3,
  "rounds": [
    {
      "roundId": "r1",
      "messageRef": "initial-message.txt",
      "receivedAt": "2026-09-01T10:05:00+08:00",
      "occurredAt": "2026-09-01T10:01:00+08:00",
      "materialView": "round-1",
      "services": ["sample-api"],
      "environment": "evaluation",
      "repos": [{"repoId": "app", "expectedSha": "cc4c13e4ae3f65fc76c23962b316df4a60e0c7e0"}]
    }
  ]
}
```

描述文件可以包含调度元数据，但不得把整份 JSON 丢进 prompt。发生时间未知用 `null`，不编造；上报时间和故障时间不互相替代。

`receivedAt` 是模拟平台事实；`occurredAt/services/environment/expectedSha` 默认是控制器的预期与预检依据，不是生产已知信息的自动注入接口。当前 routeInbound 从消息正文提服务，prepare 从本轮正文提发生时间。只有当轮消息或业务现有入口已经公开的信息，才可进入调查/模型输入；私有标准知道的服务、时间和版本不得偷偷补入。每轮核对实际 scope 与预期，暴露提取错误和跨轮信息丢失，不用评测侧回填掩盖它们。

### 6.3 私有逐轮标准

```json
{
  "schemaVersion": "prediagnosis-truth-v2",
  "caseId": "fp07-clarify",
  "rootCauseRef": "reviewed-root-cause.md",
  "rounds": [
    {
      "roundId": "r1",
      "allowedOutcomes": ["clarify", "partial_report"],
      "allowedClaimDepth": "symptom",
      "requiredFacts": ["实际响应与工单预期不符"],
      "forbiddenAssertions": ["只凭500就断言具体代码根因"],
      "materialNeeds": [{"needId": "server-error", "description": "同一请求的服务端错误详情"}],
      "evidenceRequirements": [],
      "nextInputPolicy": {"kind": "scheduled", "nextRoundId": "r2"}
    }
  ]
}
```

该示例只有首轮，完整多轮 case 必须补全全部轮次和控制器的私有未来输入。`rootCauseRef` 是制作侧真值，不能代替逐轮 allowedClaimDepth。

建议标准字段还包括：

- `acceptableClaims`：可接受的等价判断，不要求固定措辞。
- `contradictedClaims`：本轮证据已推翻的旧判断及具体反证。
- `evidenceRequirements`：每个重要判断所需的证据组合，多个组合为 OR，组合内为 AND。
- `requiredCorrections`：需要更正哪些历史判断；允许明确降级，无需必须宣布最终根因。
- `writebackRequirements`：关键信息、材料边界、可读位置、待补事项不能在回写中丢失。
- `unscorableReason`：标准或观测不足时记缺测，不能任意打零或一。
- `review`：作者、复核者、rubric hash、复核结论及分歧处理记录。

### 6.4 证据定位与支持组合

代码定位至少包含：repoId、完整 SHA、规范化 path、行范围、关键内容 hash 或关键文本锚点。必须先核对 SHA 和内容，再考虑行范围；注释或相邻行重叠不自动命中。

日志定位至少包含：源材料文件 hash、原始/转换行映射、服务、环境/所属材料视图、时间范围、请求标识（存在时）、关键内容。级别与 substring 只能作辅助。跨行栈或跨多条日志的支持关系允许组合。

```json
{
  "claimId": "validation-response-path",
  "supportsAnyOf": [
    {"allOf": ["matching-request", "server-exception", "buggy-code-path"]},
    {"allOf": ["server-exception", "equivalent-code-explanation"]}
  ]
}
```

人工复核遇到未预列但有效的证据组合，可以标记 `needs_gold_review`；复核后冻结新 gold 标识，并对受影响结果统一重评分。不得只为某个模型的错误结果临时加白名单。

## 7. 多轮运行与正式回写

### 7.1 运行模式

保留旧 `npm run eval` 作为既有单轮入口。本期新增 v2 模式，默认 `fake/scripted`；只有显式选择 `pi` 且配置预检通过才调用真实模型。具体命令名称在接入 CLI 时确定，不用新命令覆盖旧数据。

推荐主路径：每条调查轨迹一次新 Store/数据库 → routeInbound 或等价正式入站 → claim → executeRun → 正式 finalize → processDeliveriesOnce + 捕获 sender → 记录结果 → 控制器按脚本发布下一轮。

为验证正式回写，使用现有受支持 IM provider 的本地输入结构和 FakeFeishuClient/通用捕获 sender，不启动真实平台网关、不加载真实发送凭据。它只验证内部保存、渲染、排队、发送语义；真实 webhook 接入可靠性另由已有集成测试负责。

诊断语义层也可使用 `web` provider，但它不进入 IM delivery，因此不能用 web 结果冒充回写层通过。报告中分别标明执行模式。

### 7.2 轮次规则

1. 同一轨迹的全部轮次共享 investigation、会话、历史证据；每轮独立 run/attempt。同一 case 的不同 trial、新 case 使用全新状态。
2. 本轮发布后才配置它的 logDir、repo 等材料；未来材料不能已在首轮工具范围里。
3. `reply/clarify` 是有效输出类型，按补证目标评分；`reply/chat` 在诊断工单中通常不满足任务，但仍完整记录。
4. 第一版优先采用 `scheduled`：每个规定轮次运行完后按脚本补充；模型问错或未问仍如实记录，后续材料不用于挽救首轮分数。
5. `on_request` 可后续增加：通过预定义需求 ID/人工可核查匹配决定补充，不让控制器从私有根因动态生成“更有帮助”的回答。格式不支持可靠匹配时不要强行实现。
6. 反证脚本按规定轮次发布，不能只挑模型答错时给反证。测试目标是收到反证后能否合理修正。
7. 达到轮数/工具/时间/token 预算、用户不补充或运行失败时，保留当前结果并结束；不能无限追问或自动扩大读取范围。
8. 不把某一个固定调用顺序作为成功条件；有效路径可以不同。

只因模型无论何时都追问，不能获得完整成功；材料充分时不必要追问应记录效率损失或任务未完成。

### 7.3 原始输出与观测

trace 至少记录：trial/case/round/run/attempt、事件序号、输入、范围与材料视图、工具参数、实际返回文本、成功/错误、证据批次/UID、原始 assistant 公开输出或 submit_report 参数、raw EngineResult、校验 issues、最终保存报告/回复、实际发送内容、预算/usage、状态和异常。

不要求记录模型私有思维链。只记录可取得的输出、工具调用和使用量；供应商未返回字段记 `null` 和原因。

现有 executeRun 不对外暴露全部中间对象：先检查 session_entries、tool_executions、evidence_batches 等是否足够导出。原始 EngineResult 可由评测引擎装饰器捕获；原始草稿需深拷贝避免后续校验修改污染。校验 issues 无法从持久化记录恢复时，增加可选观察器，默认关闭，不改变诊断决定。

不要为了记录 trace 重做一次查询、提交或 finalize。评分侧重放 validate 只能用于分析，并应验证与真实保存结果一致，不能冒充实际执行时的校验记录。

### 7.4 异常与资源收口

- case 异常写为 `execution_error`，保留 trace，finally 关闭数据库/会话/计时器和临时资源，继续其他 case。
- 明确区分模型拒绝、材料不存在、鉴权、限流、超时、取消和评分失败。
- 重试沿用已有策略并记录每个 attempt；不得丢弃失败后只保存重试成功。
- 同一组基线使用一致重试政策。基础设施失败同时计入运行失败率，语义质量可单列有效运行分母。
- token 硬限制只有运行接口支持时才能声称已强制执行；不支持时用工具/时间/轮次硬限制并标记 token 为观测预算。

## 8. 可见性：不能只比较三组条数

### 8.1 四层定义

| 层 | 定义 | 使用目的 |
|---|---|---|
| A：sourceReturned | 本次 source 方法实际返回给工具的候选；已包含源自身的上限/过滤 | 观察取材能力；不是整个日志源/仓库所有内容 |
| B：persisted | commit 成功的证据及其入库后的内容 | 观察持久化/单条截断/提交失败 |
| C1：toolReturned | 实际交给引擎的工具返回文本中存在的关键内容 | 首期可可靠观测的主要可见性指标 |
| C2：requestContext | 某次实际模型请求上下文包含的内容 | 验证消息构建/压缩后的可见性；有请求观测才计 |
| D：reportUsed | 报告重要判断实际使用或引用的证据 | 引用有效性、关联性与语义支持 |

C2 只表示内容进入请求，不表示模型内部确实注意、理解或利用了它。未经验证的 C2 记 `null`，报告称“工具返回可见召回”，不得称已证明模型收到。

单次工具调用通常可建立 B 到 C1 的映射；跨多轮后，报告可能引用历史证据，C2 又受压缩影响，不能要求所有总计条数机械满足同一套包含关系。

### 8.2 实现与验收

- 先利用既有会话 toolResult 捕获真实文本；A 无现成记录时，用只观察一次真实调用的 source 装饰器或可选观察器，不额外查询。
- 对 B 的 item/ref 用线上 renderer 重放，核对真实 toolResult 的字节/hash。一致性是展示器验收，不代替 C2。
- 可见匹配基于关键文本/支持事实的实际显示范围。只列出文件名、证据号、摘要标题，不等于故障内容可见。
- 对 read_code 截断保留“实际展示行/字符范围”；无法可靠确定时不计 gold 命中，并记录不可判原因。
- 同一事实多次返回按标准中的事实/证据需求去重；不能靠重复查同一条扩大召回或精确率。
- 各轮同时保存当轮可见性与历史累计可见性；反证后是否仍错误引用旧内容另由判断层评分。

必须有两个观测反例：超过预览上限的命中只计 B 不计 C1；codeRef 包含 gold 行但关键内容被截断，同样不计 C1。还应检查 commit 成功但调用中断未返回，不能仅凭 B 推定 C1。

## 9. 评分设计与反例校准

### 9.1 判定顺序

评分采用“确定性硬检查 → 逐轮行为/重要判断复核 → 分维度汇总”。不以一个加权总分掩盖严重错误。

1. 检查执行是否完成、材料观测是否完整、私有标准是否有效；缺测与失败分开。
2. 检查读取边界、调查身份、SHA、内容、引用可解析性；硬失败不能被模型裁判覆盖。
3. 对照本轮允许行为与支持深度，检查 summary、confirmedFacts、全部重要 hypotheses 及 nextSteps 中的实质断言。
4. 检查引证内容能否支持对应判断；“正确根因文字 + 任意一条正确证据”仍可能失败。
5. 检查补问能否减少关键不确定性，反证是否促成恰当修正。
6. 分别给 raw、validated、writeback 结果评分。程序校验纠正了模型错误时，不能把 raw 错误抹去。

“supported”表示项目报告状态，不自动表示语义正确。材料不足时即使无 supported 假设，摘要或事实里仍可能存在越界断言。

### 9.2 指标与分母

| 指标 | 定义 | 分母/不适用处理 |
|---|---|---|
| executionSuccess | 正式链路正常取得、保存并按需要回写合法业务输出的 trial 比例；业务输出可为预诊断或合理补证 | 所有安排的真实诊断 trial；工程异常始终为失败 |
| traceCompletion | 结束状态和要求的运行记录完整保存的比例 | 所有 trial；完整记录的失败也可满足此项 |
| harnessConformance | 脚本工程自测是否达到预设行为，包括故障注入后的预期失败 | 仅工程自测；不混入真实模型执行成功率 |
| retrievedRecall | gold 需求中被 A 命中的比例 | 本轮适用的 gold 需求；没有 gold 时 null |
| persistedRecall | gold 需求中被 B 命中的比例 | 同上，仅定位工程损失 |
| toolVisibleRecall | gold 需求中被 C1 展示的比例 | 同上；首期主要取证指标 |
| requestVisibleRecall | gold 需求中被 C2 包含的比例 | 仅请求观测可验证的运行 |
| citationValidity | 重要判断引用中，身份/范围/SHA/内容有效的比例 | 去重后的实际引用；无引用时 null，另判应引未引 |
| claimSupport | 达到本轮深度且受相关可见内容支持的必要判断比例 | 人工 rubric；关键错误单列，不以平均数抵消 |
| unsupportedAssertionRate | 重要实质断言中无依据/越界的比例 | 重要断言数；没有断言时 null |
| clarificationSuccess | 不足材料轮次提出有效需求、未越界断言 | 只在需要补证的轮次 |
| contradictionUpdateSuccess | 对应反证到达后恰当修正/降级旧判断 | 只在有实质反证的轨迹 |
| writebackSuccess | 正式保存和捕获发送完成、关键信息未丢失 | 应回写轮次；真实外部送达不在本期 |
| usefulPrediagnosis | 人能据此继续查，证据可靠、边界清楚 | 人工复核的有效轨迹，按 family 单列 |

所有比率同时报告 numerator、denominator、notApplicable、unscored；`null` 不按零或一参与平均。至少报告 raw/validated/writeback 的关键错误数量及校验器纠正数量。

召回的计分单位固定为 `requirementId/factId`，不是返回证据条数。同一需求的等价 locator/证据组合为 OR，只占一个分母；满足其中一个组合的全部 AND 成员才命中该需求，部分取得另记 partial，不给完整召回。某个重要结论可能还需要多个需求一起满足，其整体充分性由 claimSupport 判断。各层使用同一版需求映射，不能通过增加等价 locator 放大分母。

每轮另列“本轮新增可见”及“截至本轮历史累计可见”，各自分子、分母和适用需求范围对应。曾经进入请求与当前请求仍包含分别记录，不因历史入库/展示推定当前 C2。仅未来轮才能获得的证据不要求首轮召回，首轮应评有效补证；没有本轮适用 gold 的召回为 null。

引用了未枚举在 gold 中但确实有效的内容，不能直接当干扰；进入 gold 复核队列。真正无关内容与已知干扰分开记录。

### 9.3 人工语义 rubric

每个重要判断记录 claim 文本、所在字段、引用、允许深度、支持结论及理由：

- `supported`：可见材料足以支持，措辞与确定程度恰当。
- `plausible_candidate`：符合材料但仍缺条件，明确作为候选；允许时可合格。
- `unsupported`：证据不足却作确定判断，或引证和判断无关。
- `contradicted`：与已公开的关键反证冲突。
- `unscorable`：gold 或观测不足，必须补标准，不能悄悄计成功。

补证成功要求问到当前真正影响判断的材料，并允许用户合理回答；“请提供更多信息”这种空泛补问不自动成功。反证成功允许撤回、降级或更新，不要求猜中私有最终答案。

初期由案例作者拟定标准，至少另一轮独立审阅；若只有同一 AI 能提供审阅，标记 `provisional`，不得宣称人工校准完成。用户确认关键业务预期，实施 AI 不自行创造真值。

第一版 CI 自动验证确定性硬检查，以及冻结人工 review 的导入、关联和汇总。首次真实运行未经人工 review 的语义项必须是 `unscored/null`；不得为了自动通过第 9.4 节的案例又用关键词冒充语义判定。硬检查通过不等于整体预诊断合格；人工评分内容通过 review 工件逐项验收。

模型裁判放后续：先冻结一组人工判定答案，对一致性、错误类型与分歧进行校准。小样本一致率很高也不能证明可靠；不因为更换了模型就视为独立验收。

### 9.4 必须覆盖的评分正反例

| 类别 | 输入/场景 | 必须得到的判断 |
|---|---|---|
| 否定正确原因 | “并非库存超时”，仍含全部关键词 | 不认定原因命中 |
| 重复禁用断言 | 先否定 Redis，后肯定 Redis 是根因 | 后一个断言不能被前面的否定豁免 |
| 入库未返回 | gold 在 B，不在 C1 | 不计工具可见召回 |
| 截断 | codeRef 包含 gold 行，excerpt 不含关键文本 | 不计可见命中/有效支持 |
| 错误 SHA | 路径/行号相同，来自其他版本 | 版本相关引用硬失败 |
| 无关片段 | UID 有效、内容真实，但不支持当前结论 | 引用有效、语义支持失败分别记录 |
| 错根因加正确引用 | 断言错误原因并顺带引 gold | 判断失败，不能引证救回 |
| 合理追问 | 关键材料确实缺失且补问有效 | 该轮补证成功，不要求 report |
| 空日志 | 时间窗未命中 | 不能断言服务健康或故障不存在 |
| 摘要越界 | hypotheses 无 supported，summary 已断言根因 | 仍判越界断言 |
| 正确局部定位 | 足以支持直接异常，未足以最终根因 | 按 allowedClaimDepth 判，不强迫猜根因 |
| 合法替代证据 | 未固定调用顺序，取得等价支持组合 | 可以成功或进入 gold 复核 |
| 无 gold | 材料不足轮次 | recall 为 null，适用分母为零 |
| 校验器救正 | raw 跨版本高置信，validated 降级 | raw 失败保留，validated 独立评分 |
| 引用不存在/跨调查 | UID 无法解析或属于别的 case | 硬失败 |
| 反证后固执 | 第二轮反证足够，仍复述已推翻结论 | 反证更新失败 |

为这些错误样本配套正例：正确否定干扰、受证据支持的判断、有效候选、正确不足材料、正常历史引用等。先证明不会乱给分，也要证明不会把所有答案一律判错。

## 10. 版本、环境与答案隔离

### 10.1 版本绑定策略

每次运行记录 `expectedFaultSha`、`resolvedToolSha`、`pinnedBy`、版本依据及材料视图。主线源码归因要求期望与实际读取 SHA 相符，且关联材料确实来自对应运行。

首期可制作 HEAD 位于原故障提交的独立只读浅仓库，保留该原始 commit 和完整 tree，隔离未来 refs/修复材料，仍用生产按时间/HEAD 选择路径；运行后核对实际 SHA。不能删文件后重建仓库却继续声明原 SHA。确需裁剪或转换时，另记 `derivedMaterialSha`、原 SHA 与内容映射，报告读取的是派生快照，不能算原始故障 SHA 读取通过。记录这是固定版本调查，不把它当成“在混合部署历史中正确选择部署 SHA”的能力证明。

不要为让按时间选版本命中而修改上游提交时间、伪造部署记录或暗中给评测专用结果。现生产准备入口没有可靠实际部署 SHA 选择闭环；相关覆盖必须如实记录为未完成。需要将显式部署 SHA 接入生产时，应另行确认这项业务范围，不能把它混在评分改造里。

完整历史、修复分支和 Git 对象不挂给 Agent；若工具只允许固定 tree，验证其可达路径。若任何工具能查 refs/history/任意文件，隔离测试必须覆盖该能力，不能只看工作目录。

### 10.2 权限预检与泄漏测试

- 配置非空服务/仓库白名单，明确 round 级日志目录及环境归属；未授权 repo/service 请求失败，不用提示词代替强制边界。
- 对路径规范化后核验最终位置；覆盖 `..`、绝对路径、Windows 路径分隔、大小写、链接/junction 等当前环境支持的绕路方式。
- 扫描可读 Git tree、日志、配置、rules、prompt、历史会话，确认没有 gold、修复补丁、参考解释、未来用户输入。
- 当前轮材料视图以文件清单和 hash 固定；只能由控制器在下一轮发布后更换。
- 工具保持已有只读能力，没有 Shell、编辑、外网 Issue/PR 检索或真实生产写操作。
- 泄漏探针放在专门工程测试材料中，分别执行列举、搜索、读取和日志查询；不能仅断言某路径不在配置数组里。
- 多 trial/case 使用全新会话、Store 和临时运行目录；规则不得注入上一例根因。跨轮保留的是同一调查材料。

现实现的只读工具提供基础约束；本轮未实施新的安全修正。实施时先做权限预检，任何可越界读取都会阻止正式评测。只修证实阻挡本期隔离的最小问题，并在收尾说明。

路径隔离无法证明模型训练时没见过公开 Bug。manifest 标明公开来源与可能污染；不将该结果表述为未见故障的无偏泛化成绩。

## 11. trace、manifest、冻结基线与归因

### 11.1 trace 事件契约

统一 envelope：schemaVersion、suiteRunId、caseId、familyId、trialId、roundId、runId、attemptId、seq、eventType、wallTime、elapsedMs、payload。

最低事件集合：`trial_started`、`round_input`、`scope_resolved`、`source_returned`、`evidence_committed`、`tool_returned`、`model_context_observed`（可选）、`engine_result_raw`、`validation_result`、`output_persisted`、`delivery_captured`、`usage`、`run_error`、`round_finished`、`trial_finished`。

记录实际事件顺序。恢复/重试保留 attempt/generation，不能把恢复重放材料算成新取证；重放事件有明确标记。禁止把 API key、Authorization 或凭据值写入日志。

### 11.2 manifest 契约

至少记录：

- suite/case/family/trial 清单、来源层、数据划分、准入标识。
- 项目完整 Git HEAD、工作区 dirty 状态及受评实现内容 hash；仅短 SHA 不足够。
- 原始材料、规范化材料、逐轮视图、源码 tree/commit、配置、触发器、包装版本、环境锁定文件 hash。
- public case、私有 gold/rubric、scorer、system prompt、rules、工具定义、renderer、模型参数 hash。
- 引擎、provider、请求模型 ID、供应商返回的模型/修订（存在时）、采样参数、seed（支持时）、上下文限制。
- Node/操作系统/时区/依赖锁定文件、评测时间锚点、Git 时间信息；日期来自输入，不使用浮动“现在”。
- 工具/轮次/时间/token 限制及哪些被强制执行、重试政策、实际 usage/耗时/成本。
- 可见性观测等级、隐私脱敏/字段归一化规则、错误与缺测清单。

使用完整 SHA-256 指纹，哈希对规范化后的路径清单加原始字节计算；排序和换行规则固定。不存在的模型修订/usage 不猜测，使用 null。manifest 记录私有标准的 hash，不必复制答案到公开报告。

### 11.3 冻结与比较

1. 先冻结材料/标准/实现/模型配置，再跑 baseline。保持当前分数，即使差也不调整 gold 迎合输出。
2. scripted/fake 用于确定性工程验收，不能作为真实模型质量成绩。
3. 真实模型每套配置首期完整跑三次，保存全部逐 case/trial 结果，报告均值、中位数、范围和波动 case；不只报最好一次。
4. 相同采样参数甚至 temperature=0 也不保证远程模型结果相同。确定性评分重放应一致，真实模型运行只要求条件可核验。
5. 比较实现或 prompt 改动时保持材料、gold、scorer 与模型配置一致；配对查看同一 family 的变化。评分协议改变时对旧 trace 重评分并明确新口径，不能直接混比旧成绩。
6. 同一故障族多个变体先在 family 内汇总，再给族间结果；同时列出原始轨迹分数，避免变体多的故障占据过高权重。
7. holdout 不用于调 prompt/rules。保留集仅有一个族时结果只能作探索，不能声称统计泛化；正式扩量应覆盖更多机制/仓库。
8. 小样本不给虚假的可靠性承诺。需要显著性或置信区间时，按独立故障族分析，不能把重复 trial 当独立故障。

### 11.4 失败归因

采用主要原因与次要标签，而不是强迫每个问题只能有一个原因：

| 分类 | 例子 |
|---|---|
| engineering | 超时、状态/恢复错误、持久化、正式回写失败；注明基础设施或评测实现 |
| material | 错服务、环境、时间、版本；关键内容未取得/被截断 |
| reasoning | 有证据但错误归因、把相关当因果、确定程度越界 |
| clarification | 未问关键材料、重复无效追问、补充后未利用 |
| contradiction | 未识别反证、未修正被推翻判断 |
| scoring | gold 不充分、判分器误判、观测不足、人工分歧 |

每个失败保存证据依据与判定者；不能从分数自动推断唯一原因。评分失败是评测可靠性问题，不能算作模型诊断失败。产品校验器相关问题归 engineering/reasoning 并加 validator 标签，与 scoring 区分。

### 12.1 必要测试

- schema/manifest：改任一日志、源码、rules、gold、模型参数改变对应 hash；同内容同规则稳定。
- 隔离：未来材料首轮不可查、答案/补丁不可达、非法 service/repo/path 被拒绝、trial 之间无污染。
- 运行：合理追问不是错误回复；补证后同调查续接；反证后可改；上限正确停止；异常不截断整套评测。
- 可见性：入库与实际返回分离、关键内容截断、重放与真实文本一致、C2 无观测时 null。
- 评分：第 9.4 节正反例、不同证据组合、逐轮深度、全部重要断言、空分母、评分重放一致。
- 回写：正式保存/渲染/投递，关键信息保留；断言没有真实外部发送；重试失败全部保留。
- 兼容：旧 benchmark/CLI 和既有诊断测试保持可用，不把旧结果文件改写为新分数。

### 12.2 最小交付清单

1. case catalog 与准入报告：主线候选至少完成一次实质资格尝试；通过的才接纳，失败的说明材料缺口。
2. 可运行 v2 小闭环：多轮、capture 回写、trace、可见性、manifest、校准评分、离线 replay。
3. 工程正反例结果；若主线尚无正式 case，明确“工程完成、真实质量基线未建立”。
4. 人工复核后的 gold/rubric、family/split 清单和覆盖缺口。
5. 真实模型基线：仅在凭据/预算就绪且主线准入成立时执行；保存全部三次结果及归因。
6. 使用说明：准备、运行、复核、重评分、比较、失败处理；注明无法验证的能力。

暂不做：自动修复/PR、远程日志平台适配、真实部署系统接入、多语言推广、模型裁判自动决策、规则自动优化、微服务故障平台重建、可视化评分网站。
