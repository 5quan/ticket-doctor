# 面试口述：Agent 长任务的可靠执行内核（ticket-doctor 第 4 亮点）

> 一句话定位：**不是"调一次模型"，而是一套把「长时诊断任务」做成可调度、可恢复、可回放、可审计的执行内核。**

---

## 0. 30 秒版（先背这段）

> 我做的不是"调一次模型"，而是一套**长时诊断任务的执行内核**。模型调用是分钟级的，不能把事务开着，所以状态和执行之间一定有窗口。我用**持久化状态机 + 租约 + 代次守卫**解决崩溃恢复和"过期执行者双提交"；用**幂等键 + 不确定态**解决投递的"发没发出去不知道"；再把每次工具调用和 token 以 **append-only 事件日志**落盘，让全程**可回放、可审计、可算成本**。

---

## 1. 背景 / 问题（把真难点摆出来）

一次诊断 = **长时任务**（分钟级）：调模型 + 查日志 + 读代码。于是必然有这些坑：

1. 这期间**不能把数据库事务开着**（分钟级 IO 持锁会拖垮库），所以"任务状态"与"实际执行"之间**一定有一个窗口**。
2. 进程会崩、租约会过期、网络会超时 → **崩溃后任务卡在 running 怎么办？**
3. 超时的执行者可能**还在跑**，另一个执行者接手了，**两个都想提交结果**怎么办？
4. 消息**发出去了但没收到平台确认**（sent / 未 sent 未知），重试会重复发、不重试会丢，怎么办？
5. 10 个 bug 同时来，怎么**不串消息、不串上下文、不重复执行**？

**难点一句话**：不在调用模型，在**执行与状态之间的那个窗口**。

---

## 2. 核心设计

**可靠执行（主体）**

1. **持久化状态机 + 短事务领取**：任务落 `runs` 表；`claim` 在一个短事务里做"选任务 + 占租约 + 建 attempt"，模型调用在**事务外**。
2. **代次守卫（generation）防双提交**：每次领取 generation+1；提交时带 `WHERE generation=? AND status='running'`。**过期执行者的提交影响 0 行，被丢弃**——"至少一次执行 + 恰好一次生效"的边界。
3. **心跳续租**：模型卡住也要能续租；续不上立即 abort，避免"僵尸执行者"。
4. **中断恢复**（详见第 3 节）。
5. **并发模型**：同调查串行 / 跨调查并行——claim 时排除"同调查已有 running"，保证同一 Bug 轮次不乱序，不同 Bug 并行。
6. **投递幂等 + 不确定态**：待发送记录有**幂等键唯一约束**，状态 `pending/sending/sent/uncertain/failed`；**发送租约过期 → 标 `uncertain`（结果未知，不当"未发送"无限重试，防重复发）**。报告 / 终态 / 待发送记录**同一事务提交**，发送失败只重试投递，**绝不重跑模型**。

**可观测 / 回放（顺带但非 printf）**

7. **typed event log**：首行 header，之后每行 `{seq, type, id, parentId, time, data}`，**单调 seq** 校验连续性、**torn-write 恢复**（丢最后半行）；事件类型 `message / usage / compaction / tool_started / tool_completed`。它同时是**审计依据 + 评测的执行轨迹 + 成本账本**。

---

## 3. 中断恢复（专门讲）

三种中断：**进程崩溃 / 租约过期 / 超时**。

机制：

- 心跳续租；续不上或租约过期 → 另一个 worker 的 **`recoverExpiredLeases`** 把 attempt 标 `interrupted`，run 按状态机回 `queued`（重试）或 `failed`。
- 重试带**指数退避 + 次数上限**；超限进 `failed`，并投递一条失败通知（诊断失败与消息发送失败分开处理）。
- **防"僵尸提交"**：过期执行者即使还活着，提交时 generation 不匹配 → 0 行影响，被丢弃。
- **可回放**：失败尝试的会话日志仍在，可复盘。

**一句话**：**中断不丢、恢复不乱、僵尸不能提交。**

## 4. 技术选型与理由

| 选型 | 理由 |
|---|---|
| Node.js + TypeScript | 单进程、异步 IO，模型/日志/源码调用天然并发 |
| SQLite（`node:sqlite`）+ WAL | 单机短事务，无原生编译依赖 |
| 短事务 `BEGIN IMMEDIATE` | 立刻取写锁，避免"先读后写"竞态 |
| 租约 + 心跳 + 代次守卫 | 替代长事务 / 分布式锁，贴合"过期执行者"问题 |
| 幂等键（UNIQUE） | 投递去重、事件去重 |
| append-only JSONL + SQLite 指针/汇总 | 事件真相源与查询分离：细节回放、库只存指针与 token 汇总 |
| worker 池 = 进程内 N 个异步循环 | 不是 N 个进程；可多开 worker 进程横向扩展（WAL + 代次已支持） |

---

## 5. 具体取舍（面试官爱听）

| 取舍 | 结论 |
|---|---|
| 长事务 vs 租约 | 分钟级 IO 不能持锁 → 用租约 + 代次 |
| 单机 SQLite vs PostgreSQL/Redis | 单机 SQLite(WAL) 够；PG 解决多机写并发（不是"持久化能力"），**有触发条件才上** |
| 单进程 vs 子进程隔离 | 模型是异步 IO，一个事件循环够；崩溃隔离由**租约恢复**覆盖，不必为隔离上子进程 |
| JSONL vs 全塞 SQLite | 事件纯 append、崩溃易恢复、可整段回放 → JSONL 当真相源，库只存指针/汇总 |
| 不确定态 vs 无限重试 | 宁可标"未知"交人工，也不自动重复发（防重复投递） |
| 重试 vs 幂等/代次 | 重试是"再试一次"，**代次守卫**才是"过期者不能提交"的关键 |

---

## 6. 结果 / 价值

- 崩溃/中断可恢复、不串不丢不重、投递可收敛、过程可回放。
- 是另外三点（**审计要证据链、评测要轨迹、成本要记账**）的**地基**——没有可回放的执行轨迹，评测和审计都建不起来。

---

## 7. 追问防守（Q&A）

- **"这不就是重试吗？"** → 关键不是重试，是**代次守卫（过期执行者不能提交）**和**不确定态（发没发出去不知道时的收敛）**。
- **"为什么不用事务包住整个任务？"** → 模型调用是分钟级 IO，不能持锁。
- **"为什么不用 Redis 分布式锁？"** → 单机不需要；且租约 + 代次比"锁"更贴合"过期执行者仍在跑"的问题。
- **"10 个 bug 一起提能扛住吗？"** → 持久化队列 + 同调查串行/跨调查并行 + 4 并发；真正瓶颈是模型限流（429 重试）。
- **"4 个是 4 个进程吗？"** → 不是，进程内 4 个异步循环；可多开 worker 进程横向扩展（WAL + 代次守卫已支持）。

---

## 8. 一句话收尾

> **中断不丢、恢复不乱、僵尸不能提交、过程可回放**——这套内核是把"通用 Agent 循环"变成"有保证的产品"的前提。
